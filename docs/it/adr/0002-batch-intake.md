# ADR 0002 — Ricezione dei lotti

**Data**: 19/09/2026 · **Stato**: accettata

## Contesto

`POST /v1/batches` è il contratto per cui il servizio esiste: una chiamata, un template, una casella, fino a 2.500 destinatari con i propri valori e file. Deve essere impossibile creare un lotto due volte per sbaglio, spedire qualcosa che non sia una PEC, o lasciare che i dati di un destinatario cambino il senso dell'HTML.

## Decisioni

| Decisione                                                                                                                 | Motivo                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Una chiamata `multipart/form-data`: una parte `batch` in JSON più una parte per file                                      | Ogni linguaggio lo fa nativamente (cURL di PHP incluso); un file comune a tutte le righe si carica una volta. L'alternativa "scarichiamo noi i vostri URL" è un vettore SSRF ed è stata scartata.                                                                                                                      |
| File scritti in streaming in una cartella di staging mentre vengono hashati, poi spostati sotto il lotto                  | Mai in memoria; una richiesta rifiutata non lascia nulla (lo staging viene rimosso in ogni percorso d'errore).                                                                                                                                                                                                         |
| Messaggi salvati **già resi** (oggetto e corpo per riga), template conservato sul lotto come riferimento                  | Ciò che è salvato è esattamente ciò che partirà e ciò che il cliente rileggerà; il worker non ha bisogno del motore dei template.                                                                                                                                                                                      |
| Rifiuto per riga di default, `options.atomic` per rifiutare tutto                                                         | Un lotto da 1.000 con due righe errate non deve bloccare 998 notifiche legali; chi preferisce tutto-o-niente lo dichiara. `ALL_MESSAGES_REJECTED` è un `422`: un lotto con zero righe non viene creato.                                                                                                                |
| I problemi di livello lotto sono `4xx` e non creano nulla; quelli di riga sono elencati nel `202`                         | Una regola sola su cui il cliente può contare: uno status d'errore significa "non è successo niente".                                                                                                                                                                                                                  |
| `Idempotency-Key` obbligatoria, impronta = JSON + ogni file (nome, dimensione, SHA-256)                                   | Un timeout non deve diventare due lotti. Il record è inserito come lock prima di iniziare, così un retry sovrapposto riceve `409 IDEMPOTENCY_IN_PROGRESS`; un tentativo fallito rimuove il lock e la chiave si può riusare. Non richiesta per `dryRun`, che non crea nulla.                                            |
| `dedupKey` unica per tenant tra lotti diversi, controllata prima dell'inserimento e imposta da un indice unico parziale   | Cintura e bretelle: il controllo preventivo dà un errore preciso per riga con l'id del messaggio precedente; l'indice intercetta la corsa tra due lotti concorrenti (`409 DEDUP_KEY_CONFLICT`, transazione annullata).                                                                                                 |
| Lotto + messaggi in una sola transazione MongoDB                                                                          | Un crash tra i due inserimenti non deve lasciare messaggi PENDING di un lotto inesistente: il worker li spedirebbe. È il motivo per cui il replica set serve anche in locale.                                                                                                                                          |
| Allowlist HTML, **rifiutare mai ripulire**; `{{nome}}` con escaping, `{{{nome}}}` grezzo ma rivalidato per riga           | Valore legale: parte ciò che il cliente ha scritto, oppure niente, con l'elenco di cosa non va. Un valore può finire solo in un testo o in un attributo tra virgolette; placeholder come nome di tag, in attributi senza virgolette, dentro `<style>` o nei commenti sono rifiutati perché lì l'escaping non protegge. |
| Immagini remote vietate, solo immagini inline `cid:`                                                                      | Un'immagine remota è un pixel di tracciamento e un problema di privacy in una comunicazione certificata.                                                                                                                                                                                                               |
| Verifica del destinatario con liste di domini dei gestori e lookup MX, `UNDETERMINED` rifiutato di default                | Una PEC a un indirizzo non PEC viene accettata dal gestore e mai consegnata. Le liste sono un punto di partenza curato (non il registro AgID) ed estensibili dal file di configurazione; sconosciuto significa "chiedi al cliente", mai "presumi PEC".                                                                 |
| Tipo di file dai primi byte con allowlist di estensioni; "dispatcher, non antivirus"                                      | Rifiutare il palesemente sbagliato (un eseguibile chiamato `.pdf`, un `.bat`), accettare i documenti. L'antivirus è compito della piattaforma.                                                                                                                                                                         |
| Dimensione per messaggio stimata dopo base64 (4/3 + overhead), controllata al limite della casella in ricezione, per riga | Costa meno di un rifiuto dal server SMTP ore dopo; per riga invece del `413` abbozzato in origine, perché con `atomic: false` una riga troppo grande non deve affondare il lotto.                                                                                                                                      |
| Replica set MongoDB in memoria per i test e2e                                                                             | La ricezione è transazioni + indici + parsing multipart reale; simulare uno qualsiasi di questi testerebbe la simulazione. `mongodb-memory-server` scarica il binario una volta.                                                                                                                                       |

## Conseguenze

- Il worker (fase 3) legge `messages` con `status: PENDING` ordinati per `nextAttemptAt`, per casella, e trova i file in `parts[].path` sotto `STORAGE_DIR`.
- Gli endpoint di lettura (fase 4) hanno già i loro indici: `tenantId` + `createdAt`/`reference`/`subTenant`/`status` sui lotti, `tenantId` + `to`/`ref`/`subTenant`/`status` sui messaggi.
- Le liste dei gestori vanno riviste contro il registro AgID prima del primo tenant in produzione; fino ad allora `options.unverifiedRecipients = "send"` è la via d'uscita per un dominio legittimo che le liste non conoscono.
