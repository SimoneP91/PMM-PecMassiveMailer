# ADR 0003 — Worker di invio

**Data**: 19/09/2026 · **Stato**: sostituita dalla [ADR 0006](0006-queues-no-database.md) (0.6.0)

## Contesto

Una PEC è una consegna legale: spedirne una due volte è una seconda notifica, perderne una è una notifica mancata. Il worker deve spedire ogni messaggio PENDING esattamente una volta al ritmo tollerato dal gestore, conservare la prova di ciò che è partito, sopravvivere a riavvii e repliche, e non indovinare mai quando non sa.

## Decisioni

| Decisione                                                                                                                                                                 | Motivo                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Un ciclo per casella, protetto da un **lease in MongoDB** (`mailbox_leases`, proprietario + scadenza, rinnovato a un terzo del TTL)                                       | I limiti del gestore appartengono alla casella, non al numero di repliche. Con N repliche del worker spedisce esattamente una per casella; il lease di un worker morto scade e un altro subentra. Niente broker, niente elezione del leader.                            |
| **Contatori di pacing in MongoDB** (`mailbox_counters`: minuto corrente, giorno UTC corrente)                                                                             | Un riavvio o il passaggio del lease a un'altra replica non deve far ripartire il minuto da zero. Scrive solo chi detiene il lease, quindi basta leggere-modificare-scrivere.                                                                                            |
| Messaggio **preso in carico atomicamente** (`findOneAndUpdate` PENDING/RETRY_SCHEDULED → SENDING, tentativi + 1) prima di costruire qualsiasi cosa                        | La presa in carico è l'unica cosa che impedisce due invii; ogni transizione successiva è condizionata allo stato che lascia.                                                                                                                                            |
| L'**EML è scritto su disco prima, poi spedito come `raw`**                                                                                                                | Ciò che è archiviato è byte per byte ciò che è partito. Il `Message-ID` è nostro e deterministico (`<id messaggio>@<dominio mittente>`): le ricevute (fase 5) lo citano, e un reinvio deciso da un operatore lo conserva.                                               |
| **Classificazione dell'esito** dai campi d'errore di nodemailer più un osservatore del protocollo che vede il `354` del server                                            | nodemailer segnala un timeout come `command: 'CONN'` ovunque avvenga. Osservare il log della transazione è l'unico modo per sapere se il server aveva già preso il messaggio. `354` visto + connessione persa = **STUCK**, mai ritentato in automatico.                 |
| `EAUTH` → **sospendere la casella** (`mailbox_states`), messaggio riportato a PENDING senza contare il tentativo                                                          | Una password rifiutata ritentata ogni pochi secondi fa bloccare la casella dal gestore. Il ciclo si ferma finché un operatore la riattiva (`mailbox activate`), e nel frattempo la ricezione risponde `423`.                                                            |
| 4xx → **RETRY_SCHEDULED** con backoff; 5xx su busta/dati → **FAILED**; 5xx a livello di connessione → riprova                                                             | Un 5xx a `RCPT TO` riguarda questo messaggio, un 5xx nel banner riguarda il server. `maxAttempts` (5) poi `FAILED` con `_MAX_ATTEMPTS`.                                                                                                                                 |
| **Recupero degli orfani**: SENDING da più di `staleSendingSeconds` → STUCK, mai rimesso in coda                                                                           | Un worker che muore tra il "354" e il "segnato SENT" lascia un messaggio dal destino ignoto; il worker successivo non deve rispedirlo. `message stuck` li elenca, `message resolve --as sent / requeue / failed` li chiude dopo un controllo sulla webmail del gestore. |
| Copia in Inviata via IMAP **dopo** il SENT, fallimento registrato sul messaggio (`sentCopy`) senza mai toccarne lo stato                                                  | La copia è una comodità per gli operatori; l'invio è già avvenuto.                                                                                                                                                                                                      |
| Connessione SMTP chiusa quando la coda è vuota; in pool (1 connessione, ≤ 100 messaggi) mentre si spedisce                                                                | I gestori chiudono comunque le connessioni inattive; una connessione nuova si riautentica, ed è anche così che ci si accorge di una password cambiata.                                                                                                                  |
| Lotto `SENT` solo quando niente è in attesa **e niente è STUCK**                                                                                                          | Un lotto con una riga STUCK non è finito; resta SENDING finché l'operatore decide.                                                                                                                                                                                      |
| Spegnimento pulito: segnale di abort, il messaggio in corso viene completato, lease rilasciati, 45 s di tolleranza                                                        | Un dialogo SMTP non si abbandona mai di proposito: è così che si creano gli STUCK.                                                                                                                                                                                      |
| Probe del worker su una porta propria (`WORKER_HEALTH_PORT`, `node:http` puro)                                                                                            | Anche il worker ha bisogno di liveness/readiness per Kubernetes; nessun motivo di caricare un framework HTTP per due risposte JSON.                                                                                                                                     |
| Test: nodemailer contro **`smtp-server`** in-process (protocollo vero, risposte pilotate), IMAP dietro un'interfaccia con un finto; Greenmail per la prova manuale/locale | Ogni ramo della macchina a stati è esercitato da risposte SMTP reali, compreso il caso "connessione caduta dopo il DATA".                                                                                                                                               |

## Conseguenze

- Gli operatori hanno tre comandi da imparare: `mailbox probe/activate/suspend`, `message stuck`, `message resolve`.
- Le ricevute della fase 5 si agganciano a `messageIdHeader`; l'EML in `emlPath` è la prova.
- Il pacing è per casella e per il worker che la detiene; se un gestore conta per IP su più caselle, `perMinute` va tarato di conseguenza.
