# ADR 0003 — Sending worker

**Date**: 2026-09-19 · **Status**: superseded by [ADR 0006](0006-queues-no-database.md) (0.6.0)

## Context

A PEC is a legal delivery: sending one twice is a second notification, losing one is a missed one. The worker must send every PENDING message exactly once at the pace the provider tolerates, keep proof of what left, survive restarts and replicas, and never guess when it does not know.

## Decisions

| Decision                                                                                                                                                           | Reason                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One loop per mailbox, guarded by a **lease in MongoDB** (`mailbox_leases`, owner + expiry, renewed at a third of its TTL)                                          | The provider's limits belong to the mailbox, not to the replica count. With N worker replicas exactly one sends per mailbox; a dead worker's lease expires and another takes over. No broker, no leader election.                                             |
| **Pacing counters in MongoDB** (`mailbox_counters`: current minute, current UTC day)                                                                               | A restart or a lease moving to another replica must not start a fresh minute. Only the lease holder writes, so read-modify-write is enough.                                                                                                                   |
| Message **claimed atomically** (`findOneAndUpdate` PENDING/RETRY_SCHEDULED → SENDING, attempts + 1) before anything is built                                       | The claim is the only thing that prevents two sends; every later transition is conditioned on the state it leaves.                                                                                                                                            |
| The **EML is written to disk first, then sent as `raw`**                                                                                                           | What is archived is byte for byte what left. `Message-ID` is ours and deterministic (`<message id>@<sender domain>`): receipts (stage 5) quote it, and an operator's resend keeps it.                                                                         |
| **Outcome classification** from nodemailer's error fields plus a protocol observer that sees the server's `354`                                                    | nodemailer reports a timeout as `command: 'CONN'` wherever it happens. Watching the transaction log is the only way to know whether the server had already taken the message. `354` seen + connection lost = **STUCK**, never retried automatically.          |
| `EAUTH` → **suspend the mailbox** (`mailbox_states`), message back to PENDING with the attempt not counted                                                         | A refused password retried every few seconds gets the mailbox locked by the provider. The loop pauses until an operator reactivates it (`mailbox activate`), and intake answers `423` meanwhile.                                                              |
| 4xx → **RETRY_SCHEDULED** with backoff; 5xx on envelope/data → **FAILED**; 5xx at connection level → retry                                                         | A 5xx to `RCPT TO` is about this message, a 5xx banner is about the server. `maxAttempts` (5) then `FAILED` with `_MAX_ATTEMPTS`.                                                                                                                             |
| **Stale recovery**: SENDING for longer than `staleSendingSeconds` → STUCK, never requeued                                                                          | A worker that dies between "354" and "marked SENT" leaves a message whose fate is unknown; the next worker must not resend it. `message stuck` lists them, `message resolve --as sent / requeue / failed` closes them after a look at the provider's webmail. |
| Sent-folder copy over IMAP **after** SENT, failure recorded on the message (`sentCopy`) and never affecting its state                                              | The copy is a convenience for operators; the send already happened.                                                                                                                                                                                           |
| Idle SMTP connection closed when the queue is empty; pooled (1 connection, ≤ 100 messages) while sending                                                           | Providers drop idle connections anyway; a fresh connection re-authenticates, which is also how a changed password is noticed.                                                                                                                                 |
| Batch `SENT` only when nothing is pending **and nothing is stuck**                                                                                                 | A batch with a STUCK row is not done; it stays SENDING until the operator decides.                                                                                                                                                                            |
| Graceful shutdown: abort signal, the message in flight is finished, leases released, 45 s grace                                                                    | An SMTP dialogue is never abandoned on purpose: that is how STUCK messages are made.                                                                                                                                                                          |
| Worker probes on their own port (`WORKER_HEALTH_PORT`, plain `node:http`)                                                                                          | Kubernetes needs liveness/readiness for the worker too; no reason to load an HTTP framework for two JSON answers.                                                                                                                                             |
| Tests: nodemailer against **`smtp-server`** in-process (real protocol, scripted answers), IMAP behind an interface with a fake; Greenmail for the manual/local run | Every branch of the state machine is exercised by real SMTP replies, including the hang-after-DATA case.                                                                                                                                                      |

## Consequences

- Operators have three commands to learn: `mailbox probe/activate/suspend`, `message stuck`, `message resolve`.
- The receipts of stage 5 match on `messageIdHeader`; the EML at `emlPath` is the evidence.
- Pacing is per mailbox and per worker holding it; if a provider counts per IP across mailboxes, `perMinute` must be set accordingly.
