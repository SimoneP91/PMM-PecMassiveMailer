# ADR 0006 — Queues instead of a database, one container per mailbox

**Date**: 2026-09-19 · **Status**: accepted · **Replaces**: the HTTP API and MongoDB of ADR 0002 to 0005

## Context

Version 0.5.1 was a multi-tenant HTTP API with a worker and MongoDB: it received batches, kept every message, attachment and receipt, and notified clients through signed webhooks. Infrastructure (who runs the platform) asked for a different shape: one container per tenant and mailbox, no database, and queues as the only input and output. In their words: the service sends; keeping track of what was sent is the sender's job.

## Decisions

| Decision                                                                                                                                    | Reason                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **One container per tenant and mailbox**, configured by environment variables only                                                          | Full isolation: a mailbox that fails, is suspended or uses too much memory does not touch the others. Each one is deployed, scaled and restarted on its own, which is how Kubernetes works.                                                                                                   |
| **No database; the service keeps nothing**                                                                                                  | The sender (the CRM) already has a database and owns the records. The service holds no personal data at rest.                                                                                                                                                                                 |
| **RabbitMQ**, three quorum queues per container: input (PECs), output (outcomes and receipts), dead letters                                 | Quorum queues are replicated and survive a broker restart. The input queue allows one active consumer (two containers during a rolling update never both send) and has a delivery limit with dead-lettering.                                                                                  |
| **One PEC per queue message**; the batch is only a label echoed back                                                                        | A message is acknowledged or returned as a whole: one PEC per message keeps "sent or not" exact.                                                                                                                                                                                              |
| **The sender's id inside the Message-ID** (`<pm.{id}@domain>`)                                                                              | Every receipt quotes the Message-ID: receipts find their PEC with no memory in the container, and the container recognises its own messages in the mailbox.                                                                                                                                   |
| **Acknowledge the input only after the outcome is confirmed** in the output queue (publisher confirms)                                      | An outcome is never lost. The cost is at-least-once delivery of events: every event has a stable `eventId` for de-duplication.                                                                                                                                                                |
| **A redelivered PEC is never resent blindly**: the acceptance receipt is looked for in the mailbox; found = `sent`, not found = `uncertain` | A redelivery means the previous handling may have sent it, and a PEC has legal value.                                                                                                                                                                                                         |
| **A failed handling goes back to the queue after a pause**                                                                                  | Verified on RabbitMQ 4.3: a message given back on purpose does not count toward the delivery limit, so without a pause a message that keeps failing would spin and hold the mailbox. The delivery limit catches the other case, a container that dies while handling (a crash counts).        |
| **Retries of temporary errors inside the container, within 25 minutes**                                                                     | RabbitMQ takes back a message not acknowledged within 30 minutes (consumer timeout).                                                                                                                                                                                                          |
| **Final subject and HTML from the sender**; checks kept: PEC recipient, HTML safety rules, size                                             | No templates: the sender composes. A rejected message costs nothing; a wrong PEC has legal effect.                                                                                                                                                                                            |
| **Pace per minute only**, in memory; no daily quota                                                                                         | The pace protects the mailbox from being blocked by the provider; counting is not the service's job.                                                                                                                                                                                          |
| **rabbitmq-client** as the RabbitMQ library                                                                                                 | It reconnects, re-declares the queues and resumes consuming by itself after a broker restart, and acknowledges only when the handler has finished. amqplib is more widespread but leaves reconnection to the application. The library is behind an interface of ours (`Queues`), in one file. |
| **No NestJS**                                                                                                                               | It was there for the HTTP API and dependency injection. A container that reads a queue has a dozen objects, wired by hand in `main.ts`; the framework, its decorators and the SWC test transform go.                                                                                          |
| **Logs to standard output, JSON**, collected by Graylog                                                                                     | No log files, nothing personal: ids, codes and counts.                                                                                                                                                                                                                                        |
| **Queues declared by the container**, or by the infrastructure with `PECMAILER_DECLARE_QUEUES=false`                                        | Works out of the box locally; infrastructure keeps control when it wants it.                                                                                                                                                                                                                  |

## Consequences

- The CRM publishes one message per PEC, reads the output queue, stores outcomes and receipts, de-duplicates by `eventId`, and decides when a batch is over (including the wait for missing receipts).
- There is no search and no download on the service side: the state of every PEC is in the CRM.
- RabbitMQ must allow messages of 64 MB (a 30 MB PEC is about 40 MB in base64 inside a message; the default limit is 16 MB).
- Without a cursor, the receipt reader re-reads the last hours of the mailbox at every start; the CRM discards the repeated events.
- Tests: unit tests with an in-memory fake, integration tests against a real RabbitMQ and Greenmail in Docker.
- Versions 0.1 to 0.5.1 (HTTP API, MongoDB, webhooks) stay in the git history; ADR 0002 to 0005 describe them.

## Amendments

0.6.1, after the review of the stage:

- The retry window counts one SMTP timeout per attempt besides the waits: 25 minutes in all.
- Dead-lettering is at least once (`x-dead-letter-strategy: at-least-once`, which requires `x-overflow: reject-publish`): a message leaves the input queue only once the dead-letter queue has stored it.
- A redelivered PEC is judged only on the rules of its own content, never again on its recipient (DNS and lists change; a PEC that left must not come out `rejected`).
- On shutdown the container stops consuming at once, while the receipt reader winds down.
- The receipt reader re-reads 24 hours at start (was 72).
