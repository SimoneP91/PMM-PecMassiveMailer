# ADR 0004 — Read side, cancellation and review of stage 3

**Date**: 2026-09-19 · **Status**: accepted

## Context

Clients must follow what they submitted: a batch at a glance, its messages in their own order, a message found by their `ref` or by recipient without knowing its batch, the exact bytes that left, and a way to stop what has not left yet. Every one of these endpoints takes an id, which makes object-level authorization (OWASP API1) the main risk of the stage.

## Decisions

| Decision                                                                                                                                                                                                                        | Reason                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Endpoints: `GET /v1/batches` (list), `/v1/batches/{id}`, `/{id}/summary?groupBy=subTenant`, `/{id}/messages`, `POST /{id}/cancel`, `GET /v1/messages` (search), `/v1/messages/{id}`, `/{id}/rendered`, `/{id}/eml`              | The contract agreed before the code, plus the batch list the indexes of stage 2 were already built for. Single-message cancel was dropped by decision (a one-off PEC is sent by hand).                                         |
| Every query starts from the tenant; an id of another tenant answers exactly like an id that does not exist (`404`, same body)                                                                                                   | Nothing to learn by guessing ids, not even their existence. Enforced by `test/e2e/tenant-isolation.e2e.spec.ts`, which calls every id-taking endpoint as the wrong tenant.                                                     |
| **Keyset (cursor) pagination**, opaque base64url cursor tagged with its list; newest first `(createdAt, _id)` for lists, `position` (the client's row order) inside a batch                                                     | Offsets skip or repeat items while the list changes, and get slower with depth. A cursor from another list is refused (`400 INVALID_CURSOR`). Not signed: tampering cannot widen a query that is already tenant-scoped.        |
| Filters: status and subTenant comma-separated; `ref` and `to` repeated (never split, a ref may contain a comma); `subject` case-insensitive contains (escaped, so literal); `createdFrom` inclusive / `createdBefore` exclusive | `to`/`from` were avoided as date names: `to` is the recipient. `to` matches case-insensitively through a stored lower-cased copy (`toLower`), so the index is used.                                                            |
| **Counters derived from the messages** (aggregation on `{batchId, status}`), not stored                                                                                                                                         | Review finding: stage 3 kept counters with `$inc` after each transition, outside a transaction; a crash between the two writes left a batch SENDING forever. Derived counters cannot drift and sum to `total` by construction. |
| **Batch completion decided from the messages** (`completeBatchIfDone`): no open message (PENDING, SENDING, RETRY_SCHEDULED, STUCK) → `SENT`, or `CANCELLED` if nothing ever left                                                | Same reason; shared by the worker and the cancel endpoint, conditioned on the batch still being open so concurrent callers agree.                                                                                              |
| Cancel: `PENDING`/`RETRY_SCHEDULED` → `CANCELLED`; `SENDING` untouched; idempotent                                                                                                                                              | An SMTP dialogue is never cut, a PEC that left cannot be recalled. The message a worker has already claimed is atomic with respect to the cancel (a message is either claimed or cancelled, never both).                       |
| EML download with **`Repr-Digest`** (RFC 9530, successor of `Digest`) carrying the SHA-256 recorded when the file was written                                                                                                   | The digest comes from the database, not from the file: a file altered on disk afterwards shows up as a mismatch instead of being vouched for.                                                                                  |
| Message history: `attemptLog` (every pass of the worker, with SMTP code and reply) and `operatorLog` (decisions on STUCK messages); `lastError` no longer overwritten by the operator                                           | The detail shows how a message got where it is. Who took an operator decision is stored but never returned by the API.                                                                                                         |
| **Heartbeat** timer renewing the mailbox lease and the in-flight message; stale recovery on `heartbeatAt`                                                                                                                       | Review finding: a paced wait or a large upload could outlive the lease (two senders on one mailbox) or the stale threshold (a live send marked STUCK).                                                                         |
| **`db sync-indexes [--dry-run]`** CLI command, run once per release                                                                                                                                                             | Review finding: `autoIndex` is off in production and the "migrate command" the code referred to did not exist, so the unique indexes behind `dedupKey` and `{batchId, ref}` would never have been created.                     |
| Queue index covers the claim sort `{mailbox, status, nextAttemptAt, createdAt, position}`                                                                                                                                       | Review finding: every claim sorted the whole due queue in memory. Messages now leave in the client's row order.                                                                                                                |

## Consequences

- Deploying a release is: build the image, run `db sync-indexes` (a Kubernetes Job), then roll out API and worker.
- The receipts of stage 5 will add `ACCEPTED`/`DELIVERED`/`NOT_DELIVERED` to the counters (already in the response) and a `receipts` array to the message detail (additive).
- Local databases created before this stage have batches with the old `counts` field and messages without `position`/`toLower`; they still work for sending, but lists show them incompletely. `docker compose down -v` starts clean.
