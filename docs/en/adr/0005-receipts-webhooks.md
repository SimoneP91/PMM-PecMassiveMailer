# ADR 0005 — Receipts, settlement and webhooks

**Date**: 2026-09-19 · **Status**: accepted

## Context

A PEC is legally meaningful through its receipts: the sender's provider issues an _accettazione_ (acceptance), the recipient's provider an _avvenuta consegna_ (delivery) or an _errore di consegna_ (non-delivery). They arrive as signed mails in the sending mailbox, each with a `daticert.xml` that states what happened. Clients want the outcome per message and a signal when a batch is over, without polling us. Stage 5 reads those receipts, closes batches for good, and pushes events to the clients.

## Decisions

| Decision                                                                                                                                                                                                                                                                         | Reason                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **One receipt reader per mailbox**, under its own lease `receipts:<code>`, separate from the sending lease                                                                                                                                                                       | A slow IMAP read never delays a send, and two workers never read the same folder at once.                                                                                                                                                          |
| The folder is opened **read-only** (`EXAMINE`, `BODY.PEEK`); progress is a **UID cursor** per mailbox and folder (`imap_cursors`), reset when `UIDVALIDITY` changes                                                                                                              | The mailbox belongs to the client and often has a human reading it too: nothing is marked as read, moved or deleted. A UID cursor survives restarts and is exact; UIDVALIDITY is IMAP's own signal that UIDs were renumbered.                      |
| A mail is a receipt **only if its top-level header has `X-Ricevuta`**; anything with `X-Trasporto` (a PEC transport envelope or an anomaly) is ignored, whatever it contains                                                                                                     | Anyone can send a PEC to the mailbox. Inside a transport envelope a sender can put a forged "receipt": the envelope is the provider vouching for the sender, not for the content. Only the provider writes `X-Ricevuta` at top level.              |
| The provider's S/MIME signature is **kept, not verified**                                                                                                                                                                                                                        | The original mail is stored byte for byte with its SHA-256 as legal proof; verification needs the AgID trust list, which is out of scope for now. The read-only IMAP account of the client's own mailbox is the trust boundary.                    |
| Matching by `X-Riferimento-Message-ID`, falling back to the daticert `<msgid>`; one receipt stored once (unique `{mailbox, dedupKey}`, the key being the receipt's own Message-ID or the SHA-256 of its bytes)                                                                   | The Message-ID we generate is unique per message; re-reading a folder after a crash must not duplicate receipts.                                                                                                                                   |
| **daticert.xml parsed with htmlparser2 in `xmlMode`**, which never expands DTD entities                                                                                                                                                                                          | XXE and "billion laughs" are impossible by construction, not by configuration. No new dependency.                                                                                                                                                  |
| **mailparser** moves from dev to runtime dependencies                                                                                                                                                                                                                            | Receipts are MIME trees (multipart/signed around multipart/mixed); mailparser, from the nodemailer author, is the mature parser already used by the tests.                                                                                         |
| **States only move forward**: ACCEPTED ← SENT/STUCK/RETRY_SCHEDULED/FAILED; DELIVERED/NOT_DELIVERED from those or ACCEPTED; a late acceptance only fills `acceptedAt`                                                                                                            | Receipts can arrive out of order. An acceptance proves the provider took the message: it resolves a STUCK message (no duplicate resend) and corrects a FAILED one.                                                                                 |
| NOT_DELIVERED also for `rilevazione-virus` and `non-accettazione`; `presa-in-carico` and `preavviso-errore-consegna` are informational only                                                                                                                                      | Only a final receipt settles a message. The warning is followed by the real non-delivery.                                                                                                                                                          |
| **Settlement** per message: `PENDING` until a final receipt (`SETTLED`), or `TIMED_OUT` after `receipts.settleAfterHours` (30 h default); FAILED and CANCELLED messages settle at once                                                                                           | PEC rules give the recipient's provider 24 h to deliver; 30 h adds margin. A batch without a closing moment is useless to a client that must decide what to do next.                                                                               |
| Batch: `SENT` when no message is open, `SETTLED` when no message is `PENDING` settlement; both decided **from the messages, in a transaction with the outbox event** (`BatchLifecycle`)                                                                                          | The same reason as the derived counters of stage 4: no second write that a crash can skip. A periodic job reconciles batches that stayed open (a crash between a message update and the check).                                                    |
| **Transactional outbox** (`webhook_events`, unique `{tenantId, dedupKey}`): the event is written in the same transaction as the state change; a dispatcher delivers it later                                                                                                     | An HTTP call inside a transaction is either lost (crash after commit) or a lie (rollback after the call). The outbox gives "happened ⇔ will be notified".                                                                                          |
| Delivery **at least once**, one event per call, `eventId` stable across retries; backoff `30s, 2m, 10m, 30m, 1h, 2h…` for `retryForHours` (24 h), then `FAILED`, retried by hand with `webhook retry <id>`                                                                       | Exactly-once over HTTP does not exist; the receiver deduplicates on the event id. 24 h covers a weekend-night outage of a CRM; beyond that a person should look.                                                                                   |
| Events: `batch.sent`, `batch.settled`, `mailbox.suspended`. Payload: ids, counters, reference, subTenant; **never recipients, subjects or bodies**                                                                                                                               | The client reads details through the authenticated API. A webhook body ends up in logs of proxies and CRMs: it must carry no personal data.                                                                                                        |
| Signature **`X-PecMailer-Signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<body>")>`** with `X-PecMailer-Timestamp`                                                                                                                                                       | The Stripe/Standard Webhooks scheme: the timestamp inside the MAC stops replays (the receiver rejects old timestamps, 5 min), the raw body stops tampering. Secret per tenant, from the environment.                                               |
| **Anti-SSRF**: HTTPS only, no redirects followed, the address is checked **after DNS resolution** (loopback, RFC 1918, link-local and cloud metadata, CGNAT, ULA, multicast, IPv4-mapped IPv6 are refused); `allowPrivateNetwork: true` per tenant for a receiver inside the VPN | The URL comes from configuration today, but a check on the host name alone is bypassed by DNS pointing at `169.254.169.254` or `127.0.0.1`. Checking the resolved address in the socket's own `lookup` leaves no window between check and connect. |
| `mailbox.suspended` recorded only when the state changes (IMAP or SMTP login refused, or operator)                                                                                                                                                                               | A login refused every minute must not flood the client with the same event.                                                                                                                                                                        |
| Liveness: a loop sleeping on purpose counts as alive until its planned wake-up                                                                                                                                                                                                   | Found while testing: with a 60 s receipt poll the probe saw the loop as idle; with a poll of 5 min or more, the container would have been restarted forever.                                                                                       |

## Review (same day)

A second reading of stages 4 and 5 found thirteen issues, fixed before release; the list is in `documentation.md` ("Review of stages 4 and 5"). The ones that changed a decision above: the reader handles one mail at a time and downloads a body only when the headers allow a receipt; a first read starts from the settlement window; an operator's suspension no longer stops reading; a receipt may also move a PENDING message (requeued by an operator); webhook secrets must be at least 32 characters; IPv4 carried in IPv6 (mapped, NAT64) is judged as IPv4.

## Consequences

- Deploying 0.5.0: build the image, run `db sync-indexes` (new collections `receipts`, `imap_cursors`, `webhook_events`, new message indexes), roll out. New optional config sections `receipts` and `webhooks`.
- The receipt reader needs the IMAP section of each mailbox, the same credentials as the Sent copy. A refused IMAP login suspends the mailbox, sending included: the same password serves both.
- Clients that want webhooks must verify the signature and deduplicate by `X-PecMailer-Event-Id` (documented with a PHP example in `documentation.md`).
- Receipts that match no message (sent by the old system, or by hand) are ignored and left in the folder.
- Not done: verification of the provider's S/MIME signature against the AgID list; a per-message webhook (a batch event plus the API was preferred, to keep the volume bounded).
