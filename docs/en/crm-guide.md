# pecmailer — guide for the CRM and its AI assistant

How the CRM sends PECs through pecmailer and handles everything that comes back. It is written so that an AI assistant working in the CRM's codebase can follow it on its own, without seeing the pecmailer project; it works for a person just as well.

> **For whoever installs it.** Copy this file into the CRM project, e.g. as `docs/pecmailer.md`, and add to the CRM's `CLAUDE.md` (create it if missing) the line:
> `For anything about sending PECs, read and follow docs/pecmailer.md.`
> Valid for pecmailer 0.6.x, message contract version 1.

## 1. pecmailer in short

pecmailer is a service that sends PECs (Italian certified e-mail). It runs in containers, one per PEC mailbox. The CRM **never calls it directly**: it talks to it only through RabbitMQ, a queue system. A queue is a letterbox: the writer drops a message, the reader takes it when ready, and meanwhile the message is safe.

```
CRM ──(1) puts the PEC──► pecmailer.<tenant>.<mailbox>.in  ──► pecmailer ──► PEC provider ──► recipient
CRM ◄─(2) reads outcomes── pecmailer.<tenant>.<mailbox>.out ◄──┘
                           pecmailer.<tenant>.<mailbox>.dead  (unreadable messages: a person looks at them)
```

- Each mailbox has its three queues. Example: `pecmailer.serfin.serfin-legalmail.in`.
- pecmailer **keeps nothing**: no messages, no attachments, no receipts. The state of every PEC and the receipts, which are the legal proof, are kept **by the CRM**.
- pecmailer keeps the mailbox's pace by itself: 60 PECs a minute with the default settings. The CRM may queue thousands of PECs at once; they leave at the right pace.
- For each PEC, pecmailer publishes one **outcome** (sent, rejected, failed, uncertain), then every **receipt** of the provider as it arrives.

## 2. Non-negotiable rules

1. **A PEC must never leave twice.** Every PEC has a new `id`, generated by the CRM and never reused. A PEC sent again gets a new id.
2. **Database first, then the queue.** The PEC is recorded in the CRM's database _before_ it is queued: there is never a PEC the CRM knows nothing about.
3. **An outcome must never be lost.** The CRM acknowledges an event to RabbitMQ (`ack`) only _after_ storing it in the database, in the same transaction.
4. **Copies are normal.** The same event can arrive twice (after a restart pecmailer publishes the receipts of the last 24 hours again). Every event has a stable `eventId`: the CRM keeps those it has seen and discards copies.
5. **Receipts are the legal proof**: stored whole, as they arrive, after checking their SHA-256, and kept for as long as the company's rules require.
6. **The queues belong to pecmailer.** The CRM does not create, delete, purge or reconfigure them. It only writes to `.in` queues and only reads from `.out` queues.
7. **No credentials in the code.** The RabbitMQ user and password come from environment variables or the CRM's secret store.

## 3. Directives for the CRM's AI assistant

- Before writing code, **explore the CRM**: PHP version, framework (or hand-written code), database, how it runs in production, and how it sends PECs today. **Ask before removing or changing the old sending code.**
- Adapt the reference code of section 8 to the CRM's conventions (folders, names, migrations, tests), **without changing the behaviour** described in sections 2, 5 and 6.
- **Do not change the message format.** If something the contract does not offer is needed, stop and ask: the contract changes on pecmailer's side.
- **Never send real PECs** and never point at production queues unless explicitly asked. The local stack (section 10) is for trying.
- **Never write passwords** in code, in versioned configuration or in the chat.
- Every state rule (section 6) has a test. The sample events of section 9 are ready for tests.
- Publishing and reading outcomes are **two separate processes**: whoever queues PECs (a page, a campaign job) does not wait for outcomes.
- Follow the CRM project's rules on commits and reviews.

## 5. The message contract

### The PEC to send (`.in` queue)

One JSON message per PEC, with AMQP properties `content_type: application/json`, `delivery_mode: 2` (persistent) and `message_id` equal to the `id`.

| Field                         | Required | Rules                                                                                                                                                                     |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`                     | yes      | Always `1`                                                                                                                                                                |
| `id`                          | yes      | Letters, digits, `.`, `_`, `-`; 1 to 64 characters; unique for ever. Recommended: 32 random hex characters. The recipient sees it inside the Message-ID: no personal data |
| `reference`                   | no       | A CRM label, e.g. the case number; at most 200 characters. Returned in the outcomes                                                                                       |
| `batch`                       | no       | A group label, e.g. the campaign; at most 200 characters. Returned in the outcomes                                                                                        |
| `to.address`                  | yes      | The recipient's PEC address; at most 254 characters                                                                                                                       |
| `to.name`                     | no       | The recipient's name; at most 200 characters, no line breaks                                                                                                              |
| `subject`                     | yes      | The final subject; 1 to 500 characters, no line breaks                                                                                                                    |
| `html`                        | yes      | The final text in HTML; at most 512 KB                                                                                                                                    |
| `attachments`                 | no       | Up to 50: `{ "filename": "...", "content": "<base64>" }`                                                                                                                  |
| `inlineImages`                | no       | Up to 20 images in the text: `{ "cid": "logo", "content": "<base64>", "filename": "..." }`, used as `<img src="cid:logo">`                                                |
| `options.unverifiedRecipient` | no       | `reject` (default) or `send`: what to do when the domain cannot be established as PEC                                                                                     |

Unknown fields get the message rejected. The whole PEC, attachments included, must fit the mailbox limit (30 MB by default).

What pecmailer checks before sending. When something is wrong, the PEC does not leave and a `rejected` outcome arrives:

- **Recipient**: must be a PEC address; ordinary mail domains such as gmail.com are refused.
- **HTML**: a closed list of elements; no scripts, forms, frames, remote images, styles with `url()`; links only `https`, `http`, `mailto`. Images go in `inlineImages`.
- **Attachments**: the type is detected from the content, not the name. Allowed extensions: pdf, p7m, xml, txt, csv, rtf, eml, zip, doc, docx, xls, xlsx, ppt, pptx, odt, ods, png, jpg, jpeg, gif. Executables and scripts always refused.

### The events (`.out` queue)

Every event is JSON and always has `version` (1), `event`, `eventId`, `occurredAt` (ISO date), `tenant`, `mailbox`. The AMQP `type` property is the event name, `message_id` the `eventId`.

| `event`             | `eventId`                            | Own fields                                                                                                                                                                                                             | Meaning                                                                                                                            |
| ------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `sent`              | `sent:<id>`                          | `id`, `reference`, `batch`, `messageId`, `sentAt`, `confirmedBy` (`SMTP` or `ACCEPTANCE_RECEIPT`), `smtpResponse`, `attempts`, `sentCopy` (`ARCHIVED`, `FAILED`, `DISABLED`, `UNKNOWN`), `sentCopyError`, `warnings[]` | The provider took the PEC                                                                                                          |
| `rejected`          | `rejected:<id>`                      | `id`, `reference`, `batch`, `errors[]` (`code`, `field`, `detail`)                                                                                                                                                     | Not sent: the message breaks a rule                                                                                                |
| `failed`            | `failed:<id>`                        | `id`, `reference`, `batch`, `code`, `smtpCode`, `detail`, `attempts`                                                                                                                                                   | Not sent: the provider refused it, or temporary errors persisted to the last attempt (about 21 minutes)                            |
| `uncertain`         | `uncertain:<id>`                     | `id`, `reference`, `batch`, `messageId`, `reason`, `detail`                                                                                                                                                            | Whether it left is unknown                                                                                                         |
| `receipt`           | `receipt:<sha256>`                   | `id`, `messageId`, `receiptType`, `final`, `issuedAt`, `provider`, `recipient`, `error` (`code`, `detail`), `providerId`, `receiptMessageId`, `eml` (base64), `emlSha256`, `daticert` (base64)                         | A provider's receipt, whole                                                                                                        |
| `mailbox.suspended` | `mailbox.suspended:<mailbox>:<date>` | `cause` (`SMTP_AUTH_REFUSED` or `IMAP_AUTH_REFUSED`), `detail`                                                                                                                                                         | The provider refused the password: the mailbox is stopped until restarted with the right one. PECs wait in the queue, none is lost |

`reference`, `batch`, `smtpResponse`, `sentCopyError`, `smtpCode`, `provider`, `recipient`, `error`, `providerId`, `receiptMessageId` and `daticert` may be missing. Receipts carry only `id`: the CRM finds the rest from it.

| `receiptType`          | What it is                                                                                                     | `final` |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | ------- |
| `ACCEPTANCE`           | The sender's provider accepted it: from here the PEC has legal value                                           | no      |
| `TAKING_CHARGE`        | The recipient's provider took charge of it                                                                     | no      |
| `NON_DELIVERY_WARNING` | Warning of a possible non-delivery                                                                             | no      |
| `DELIVERY`             | Delivered                                                                                                      | yes     |
| `NON_DELIVERY`         | Not delivered; the reason is in `error.detail` (Aruba reports a missing mailbox with the generic code `altro`) | yes     |
| `NON_ACCEPTANCE`       | Not accepted by the sender's provider                                                                          | yes     |
| `VIRUS_DETECTED`       | Refused because of a virus                                                                                     | yes     |

`rejected` codes: `INVALID_MESSAGE`, `RECIPIENT_NOT_PEC`, `RECIPIENT_UNVERIFIED`, `FORBIDDEN_ELEMENT`, `FORBIDDEN_ATTRIBUTE`, `FORBIDDEN_CSS`, `FORBIDDEN_URL`, `FORBIDDEN_NODE`, `FORBIDDEN_DIRECTIVE`, `EXTERNAL_IMAGE`, `UNDECLARED_INLINE_IMAGE`, `INLINE_IMAGE_NOT_IMAGE`, `EXECUTABLE`, `EXTENSION_NOT_ALLOWED`, `CONTENT_MISMATCH`, `MESSAGE_TOO_LARGE`. `failed` codes: `SMTP_<code>` (e.g. `SMTP_550`) or `RETRIES_EXHAUSTED`. In `sent` events the warning `UNUSED_INLINE_IMAGE` flags an image given but not used: the PEC leaves anyway.

The contract only grows by adding fields or events: the CRM must **ignore fields it does not know** and keep events it does not know without stopping. A `version` other than 1 means a new contract: the CRM does not process it and reports it.

## 6. The states of a PEC in the CRM

| State                            | When                                                         | What to do                                                                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IN_ACCODAMENTO` (being queued)  | Recorded; publishing in progress or unanswered               | Nothing. If it stays so for more than 35 minutes, an alert calls a person (below)                                                                                                                                                   |
| `DA_ACCODARE` (to queue)         | RabbitMQ said no explicitly, or the queue does not exist     | The periodic job publishes it again **with the same id**: safe, as RabbitMQ did not store it                                                                                                                                        |
| `IN_CODA` (queued)               | RabbitMQ confirmed it stored it                              | Wait                                                                                                                                                                                                                                |
| `RIFIUTATA` (rejected)           | `rejected` outcome                                           | Fix and send again with **a new id**                                                                                                                                                                                                |
| `FALLITA` (failed)               | `failed` outcome                                             | Read the reason; send again with **a new id** if appropriate                                                                                                                                                                        |
| `DA_VERIFICARE` (to check)       | `uncertain` outcome                                          | **Never resend blindly.** If the acceptance arrives, the state moves to `ACCETTATA` by itself. Otherwise a person checks (the mailbox's Sent folder, the receipts) and only when sure it did not leave sends it again with a new id |
| `SPEDITA` (sent)                 | `sent` outcome                                               | Wait for the receipts                                                                                                                                                                                                               |
| `ACCETTATA` (accepted)           | `ACCEPTANCE` receipt                                         | Wait for the delivery                                                                                                                                                                                                               |
| `CONSEGNATA` (delivered)         | `DELIVERY` receipt                                           | Done                                                                                                                                                                                                                                |
| `NON_CONSEGNATA` (not delivered) | `NON_DELIVERY`, `NON_ACCEPTANCE` or `VIRUS_DETECTED` receipt | Done; the reason is in the detail                                                                                                                                                                                                   |

The state names are Italian, as in the reference code; the CRM may rename them.

**The state only moves towards safer knowledge**, in this order:

| Rank | States                          |
| ---- | ------------------------------- |
| 0    | `IN_ACCODAMENTO`, `DA_ACCODARE` |
| 1    | `IN_CODA`                       |
| 2    | `RIFIUTATA`, `FALLITA`          |
| 3    | `DA_VERIFICARE`                 |
| 4    | `SPEDITA`                       |
| 5    | `ACCETTATA`                     |
| 6    | `CONSEGNATA`, `NON_CONSEGNATA`  |

An event that would lead to an equal or lower rank is kept but does not change the state. So:

- a receipt arriving before the `sent` outcome, which can happen, is not overtaken;
- copies do no harm;
- in the very rare case of two different outcomes for the same PEC (e.g. `failed` then `uncertain`, when pecmailer stops at the wrong instant), `DA_VERIFICARE` wins, as it should;
- `TAKING_CHARGE` and `NON_DELIVERY_WARNING` are kept without changing the state.

**`IN_ACCODAMENTO` for more than 35 minutes** means RabbitMQ did not answer, or the process stopped while publishing: the PEC may or may not be in the queue. Publishing it again blindly risks a double send, so a person decides. It is safe to publish it again with the same id only when, on the RabbitMQ page, that mailbox's `.in` and `.out` queues are empty ("Unacked" at zero too) and no event arrived for that id. Then it is moved to `DA_ACCODARE` and the periodic job publishes it. A rare case.

## 7. The CRM side, piece by piece

1. **The tables** `pec_invii`, `pec_eventi`, `pec_ricevute` (section 8.1).
2. **The class that queues** (8.2): records the PEC, publishes it, waits for RabbitMQ's confirmation.
3. **The outcome reader** (8.3): an always-on program that reads the `.out` queues of every mailbox, discards copies, updates states, stores receipts, and acknowledges only after storing. Keep it running with something that restarts it: supervisord, systemd, a container. One is enough for all the mailboxes of a tenant.
4. **The periodic job** (8.4), e.g. every 5 minutes: publishes the `DA_ACCODARE` PECs again and raises alerts.
5. **Alerts** to a person: suspended mailbox, PECs to check, PECs stuck too long in an intermediate state.
6. **The CRM's pages**: the state of every PEC by case and by campaign, receipt downloads.

A PEC to publish again is always rebuilt from the CRM's data: the function that builds it the first time rebuilds it for publishing again with the same id. No need to keep the message, which with its attachments can weigh tens of MB.

## 8. Reference code

PHP 8, PDO and MySQL; no framework. Adapt it to the CRM, keeping its behaviour. Names and comments are in Italian, as in the CRM.

### 8.1 The tables

```sql
CREATE TABLE pec_invii (
  id            CHAR(32)     NOT NULL PRIMARY KEY,  -- the id given to pecmailer
  casella       VARCHAR(63)  NOT NULL,              -- the mailbox, e.g. serfin-legalmail
  pratica       VARCHAR(200) NULL,                  -- the "reference"
  campagna      VARCHAR(200) NULL,                  -- the "batch"
  destinatario  VARCHAR(254) NOT NULL,
  oggetto       VARCHAR(500) NOT NULL,
  stato         VARCHAR(20)  NOT NULL,
  dettaglio     TEXT         NULL,                  -- reason of a rejection, a failure, a non-delivery
  message_id    VARCHAR(320) NULL,
  creata_il     DATETIME     NOT NULL,
  aggiornata_il DATETIME     NOT NULL,
  INDEX (stato, aggiornata_il), INDEX (pratica), INDEX (campagna)
);

CREATE TABLE pec_eventi (                           -- events already processed: how copies are discarded
  event_id    VARCHAR(150) NOT NULL PRIMARY KEY,
  pec_id      CHAR(32)     NULL,
  tipo        VARCHAR(30)  NOT NULL,
  ricevuto_il DATETIME     NOT NULL,
  INDEX (pec_id)
);

CREATE TABLE pec_ricevute (
  event_id   VARCHAR(150) NOT NULL PRIMARY KEY,
  pec_id     CHAR(32)     NOT NULL,
  tipo       VARCHAR(30)  NOT NULL,                 -- ACCEPTANCE, DELIVERY, NON_DELIVERY...
  emessa_il  DATETIME     NOT NULL,
  eml_sha256 CHAR(64)     NOT NULL,
  percorso   VARCHAR(500) NOT NULL,                 -- where the .eml file is: the legal proof
  INDEX (pec_id)
);
```

### 8.2 Queuing

The class is the same as in the Italian guide, [docs/it/guida-crm.md](../it/guida-crm.md), section 8.2; here with English comments.

```php
<?php
declare(strict_types=1);

use PhpAmqpLib\Channel\AMQPChannel;
use PhpAmqpLib\Connection\AMQPStreamConnection;
use PhpAmqpLib\Exception\AMQPTimeoutException;
use PhpAmqpLib\Message\AMQPMessage;

/** Puts PECs in pecmailer's queues. One connection per process: for a campaign, one object and a loop. */
final class CodaPec
{
    private AMQPChannel $canale;
    private ?bool $confermata = null;
    private bool $respinta = false;

    public function __construct(
        private PDO $db,
        AMQPStreamConnection $rabbit,
        private string $cliente,                     // the tenant, e.g. "serfin"
    ) {
        $this->canale = $rabbit->channel();
        $this->canale->set_ack_handler(function (): void { $this->confermata = true; });    // stored
        $this->canale->set_nack_handler(function (): void { $this->confermata = false; });  // not stored
        $this->canale->set_return_listener(function (): void { $this->respinta = true; });  // no such queue
        $this->canale->confirm_select();
    }

    /** Records a new PEC and queues it. $pec holds the contract's fields but "version" and "id". Returns the id. */
    public function accoda(string $casella, array $pec): string
    {
        $id = bin2hex(random_bytes(16));
        $this->db->prepare(
            "INSERT INTO pec_invii (id, casella, pratica, campagna, destinatario, oggetto, stato, creata_il, aggiornata_il)
             VALUES (?, ?, ?, ?, ?, ?, 'IN_ACCODAMENTO', NOW(), NOW())"
        )->execute([$id, $casella, $pec['reference'] ?? null, $pec['batch'] ?? null, $pec['to']['address'], $pec['subject']]);
        $this->pubblica($id, $casella, $pec);

        return $id;
    }

    /** Publishes a DA_ACCODARE PEC again: RabbitMQ did not store it, so the same id is safe. */
    public function ripubblica(string $id, string $casella, array $pec): void
    {
        $presa = $this->db->prepare(
            "UPDATE pec_invii SET stato = 'IN_ACCODAMENTO', aggiornata_il = NOW() WHERE id = ? AND stato = 'DA_ACCODARE'"
        );
        $presa->execute([$id]);
        if ($presa->rowCount() !== 1) {
            throw new RuntimeException("PEC $id is not DA_ACCODARE: not published again");
        }
        $this->pubblica($id, $casella, $pec);
    }

    private function pubblica(string $id, string $casella, array $pec): void
    {
        $this->confermata = null;
        $this->respinta = false;
        $messaggio = new AMQPMessage(
            json_encode(['version' => 1, 'id' => $id] + $pec, JSON_THROW_ON_ERROR),
            [
                'content_type' => 'application/json',
                'delivery_mode' => AMQPMessage::DELIVERY_MODE_PERSISTENT, // survives a RabbitMQ restart
                'message_id' => $id,
            ],
        );
        // The last "true" (mandatory) sends the message back when the queue does not exist:
        // without it, with a wrong mailbox name, the PEC would vanish silently.
        $this->canale->basic_publish($messaggio, '', "pecmailer.{$this->cliente}.$casella.in", true);

        try {
            $this->canale->wait_for_pending_acks_returns(10.0);
        } catch (AMQPTimeoutException) {
            return; // no answer: stays IN_ACCODAMENTO (section 6)
        }
        if ($this->respinta || $this->confermata === false) {
            $this->cambiaStato($id, 'DA_ACCODARE');
            if ($this->respinta) {
                throw new RuntimeException("Queue pecmailer.{$this->cliente}.$casella.in does not exist");
            }
            return;
        }
        if ($this->confermata === true) {
            $this->cambiaStato($id, 'IN_CODA');
        }
    }

    private function cambiaStato(string $id, string $stato): void
    {
        // Only from IN_ACCODAMENTO: an outcome that arrived meanwhile is not overtaken.
        $this->db->prepare(
            "UPDATE pec_invii SET stato = ?, aggiornata_il = NOW() WHERE id = ? AND stato = 'IN_ACCODAMENTO'"
        )->execute([$stato, $id]);
    }
}
```

### 8.3 The outcome reader

```php
<?php
declare(strict_types=1);
require __DIR__ . '/vendor/autoload.php';

use PhpAmqpLib\Connection\AMQPStreamConnection;
use PhpAmqpLib\Message\AMQPMessage;

/** The state only moves towards safer knowledge (section 6). */
const RANGO = [
    'IN_ACCODAMENTO' => 0, 'DA_ACCODARE' => 0, 'IN_CODA' => 1,
    'RIFIUTATA' => 2, 'FALLITA' => 2, 'DA_VERIFICARE' => 3, 'SPEDITA' => 4,
    'ACCETTATA' => 5, 'CONSEGNATA' => 6, 'NON_CONSEGNATA' => 6,
];

$db = new PDO(getenv('DB_DSN'), getenv('DB_USER'), getenv('DB_PASSWORD'), [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$rabbit = new AMQPStreamConnection(
    getenv('RABBITMQ_HOST'), (int) getenv('RABBITMQ_PORT'),
    getenv('RABBITMQ_USER'), getenv('RABBITMQ_PASSWORD'), getenv('RABBITMQ_VHOST') ?: '/',
);
$canale = $rabbit->channel();
$canale->basic_qos(0, 10, false); // at most 10 events in progress at a time

$gestisci = function (AMQPMessage $messaggio) use ($db): void {
    $db->beginTransaction();
    try {
        $evento = json_decode($messaggio->getBody(), true, 512, JSON_THROW_ON_ERROR);
        $nuovo = $db->prepare('INSERT IGNORE INTO pec_eventi (event_id, pec_id, tipo, ricevuto_il) VALUES (?, ?, ?, NOW())');
        $nuovo->execute([$evento['eventId'], $evento['id'] ?? null, $evento['event']]);
        if ($nuovo->rowCount() === 1) {   // 0 = seen before: a copy, acknowledged and nothing else
            applica($db, $evento);
        }
        $db->commit();
        $messaggio->ack();                // only now: the database has the event
    } catch (Throwable $errore) {
        $db->rollBack();
        error_log('pecmailer: event not stored, retrying: ' . $errore->getMessage());
        sleep(5);                         // no spinning if the problem persists
        $messaggio->nack(true);           // back to the queue
    }
};

$cliente = getenv('PECMAILER_CLIENTE');
foreach (explode(',', getenv('PECMAILER_CASELLE')) as $casella) {
    $canale->basic_consume("pecmailer.$cliente." . trim($casella) . '.out', '', false, false, false, false, $gestisci);
}
while ($canale->is_consuming()) {
    $canale->wait();
}

function applica(PDO $db, array $e): void
{
    if (($e['version'] ?? null) !== 1) {
        // A new contract: not processed. It stays in the queue and shows in the logs until the CRM is updated.
        throw new RuntimeException('event with unknown version: ' . json_encode($e['version'] ?? null));
    }
    switch ($e['event']) {
        case 'sent':
            avanza($db, $e['id'], 'SPEDITA', null, $e['messageId']);
            break;
        case 'rejected':
            avanza($db, $e['id'], 'RIFIUTATA', json_encode($e['errors'], JSON_UNESCAPED_UNICODE));
            break;
        case 'failed':
            avanza($db, $e['id'], 'FALLITA', $e['code'] . ': ' . $e['detail']);
            break;
        case 'uncertain':
            avanza($db, $e['id'], 'DA_VERIFICARE', $e['detail'], $e['messageId']);
            avvisa("PEC {$e['id']} to check: {$e['detail']}");
            break;
        case 'receipt':
            salvaRicevuta($db, $e);
            break;
        case 'mailbox.suspended':
            avvisa("Mailbox {$e['mailbox']} suspended ({$e['cause']}): {$e['detail']}. PECs wait in the queue.");
            break;
        default:
            // A new event from a future version: kept in pec_eventi, nothing else.
            break;
    }
}

function salvaRicevuta(PDO $db, array $e): void
{
    $file = base64_decode($e['eml'], true);
    if ($file === false || hash('sha256', $file) !== $e['emlSha256']) {
        throw new RuntimeException('damaged receipt: ' . $e['eventId']);
    }
    $percorso = getenv('PEC_CARTELLA_RICEVUTE') . "/{$e['id']}/{$e['emlSha256']}.eml";
    if (!is_dir(dirname($percorso))) {
        mkdir(dirname($percorso), 0750, true);
    }
    file_put_contents($percorso, $file);
    $db->prepare('INSERT INTO pec_ricevute (event_id, pec_id, tipo, emessa_il, eml_sha256, percorso) VALUES (?, ?, ?, ?, ?, ?)')
        ->execute([$e['eventId'], $e['id'], $e['receiptType'], date('Y-m-d H:i:s', strtotime($e['issuedAt'])), $e['emlSha256'], $percorso]);

    $stato = match ($e['receiptType']) {
        'ACCEPTANCE' => 'ACCETTATA',
        'DELIVERY' => 'CONSEGNATA',
        'NON_DELIVERY', 'NON_ACCEPTANCE', 'VIRUS_DETECTED' => 'NON_CONSEGNATA',
        default => null,                  // taking charge, warning: kept, the state does not change
    };
    if ($stato !== null) {
        avanza($db, $e['id'], $stato, $e['error']['detail'] ?? null);
    }
}

function avanza(PDO $db, string $id, string $stato, ?string $dettaglio = null, ?string $messageId = null): void
{
    if ($messageId !== null) {
        $db->prepare('UPDATE pec_invii SET message_id = ? WHERE id = ?')->execute([$messageId, $id]);
    }
    $riga = $db->prepare('SELECT stato FROM pec_invii WHERE id = ? FOR UPDATE');
    $riga->execute([$id]);
    $attuale = $riga->fetchColumn();
    if ($attuale === false) {
        return;                           // a PEC the CRM does not know (e.g. a collaudo one): event kept, nothing else
    }
    if (RANGO[$stato] <= RANGO[$attuale]) {
        return;
    }
    $db->prepare('UPDATE pec_invii SET stato = ?, dettaglio = COALESCE(?, dettaglio), aggiornata_il = NOW() WHERE id = ?')
        ->execute([$stato, $dettaglio, $id]);
}

/** To be written with the CRM's tools: an e-mail, a notification, a message to whoever must act. */
function avvisa(string $testo): void
{
    error_log('pecmailer ALERT: ' . $testo);
}
```

Keeping it running, e.g. with supervisord:

```ini
[program:pec-esiti]
command=php /path/to/crm/bin/pec-esiti.php
autostart=true
autorestart=true
startretries=999
stopwaitsecs=30
```

If the reader stops halfway through an event, nothing is lost: the event was not acknowledged, RabbitMQ delivers it again, and `pec_eventi` discards what was already stored. If the connection to RabbitMQ drops, the script ends with an error and supervisord restarts it.

### 8.4 The periodic job

Every 5 minutes, e.g. with cron.

**Publish the `DA_ACCODARE` PECs again:** rebuild each message from the CRM's data, with the same function as the first time, and call `$coda->ripubblica($id, $casella, $pec)`.

**Alerts**, with thresholds to tune on experience:

| Condition                  | Query                                                                     | Why                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Publishing without answer  | `stato = 'IN_ACCODAMENTO' AND aggiornata_il < NOW() - INTERVAL 35 MINUTE` | A person decides (section 6)                                                                                                                   |
| Stuck in the queue         | `stato = 'IN_CODA' AND aggiornata_il < NOW() - INTERVAL 3 HOUR`           | At 60 PECs a minute a 5,000-PEC campaign takes about an hour and a half. Beyond that the mailbox may be suspended or the message dead-lettered |
| Sent, no acceptance        | `stato = 'SPEDITA' AND aggiornata_il < NOW() - INTERVAL 1 HOUR`           | The acceptance normally arrives within seconds                                                                                                 |
| Accepted, no final outcome | `stato = 'ACCETTATA' AND aggiornata_il < NOW() - INTERVAL 26 HOUR`        | By the PEC rules delivery or non-delivery arrives within 24 hours                                                                              |
| To check                   | `stato = 'DA_VERIFICARE'`                                                 | Always needs a person                                                                                                                          |

## 9. Sample events, for tests

The same six events as in the Italian guide, section 9: [docs/it/guida-crm.md](../it/guida-crm.md). In receipt tests, fill `eml` and `emlSha256` from a real file: `base64_encode($eml)` and `hash('sha256', $eml)`.

Minimum tests:

- every event leads to the right state;
- a copy changes nothing;
- an `ACCEPTANCE` receipt arriving before `sent` leaves `ACCETTATA`;
- `failed` followed by `uncertain` gives `DA_VERIFICARE`;
- a receipt with a wrong digest is neither stored nor acknowledged;
- an event of unknown type is kept without errors;
- `version` 2 is not processed.

## 10. Trying it locally, without production

The pecmailer project has a complete Docker stack: RabbitMQ, a fake PEC provider (Greenmail) and two test mailboxes. It starts like this (details in its `docs/en/getting-started.md`):

```bash
git clone https://github.com/SimoneP91/PMM-PecMassiveMailer.git
cd PMM-PecMassiveMailer
docker compose up -d --build --wait
```

The CRM connects with host `localhost`, port `5672`, user and password `pecmailer`, virtual host `/`, tenant `serfin`, mailboxes `serfin-aruba` and `serfin-legalmail`. RabbitMQ page: http://localhost:15672.

- Every PEC ends up in Greenmail, even for a real recipient address: nothing leaves the local stack. `sent` outcomes come back. The `pec.example` domain is accepted as PEC on purpose, for examples; an ordinary mail domain such as gmail.com gives `rejected`, a good way to try that case.
- **Greenmail issues no receipts.** To try the reader on receipts, locally and only locally, publish the sample events of section 9 by hand into the `.out` queue, also from the RabbitMQ page (queue, then "Publish message").
- Real receipts only come with a real PEC mailbox: that collaudo is done by people, with pecmailer's procedure.

## 11. Going to production

1. The CRM complete and tried locally (section 10).
2. A collaudo with a real mailbox and a few recipients of your own: outcomes, receipts, states, stored files.
3. The go-ahead of whoever runs the infrastructure: queues, users, permissions, alerts.
4. A small first campaign, a few dozen PECs, watching states and alerts; then larger ones.

## 12. Glossary

| Word                   | Meaning                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| PEC                    | Posta elettronica certificata: an e-mail with legal value, thanks to the provider's receipts |
| Provider               | Who supplies the PEC mailbox: Aruba, Legalmail (InfoCert), Namirial...                       |
| Acceptance receipt     | The sender's provider took the PEC: from here it has legal value                             |
| Delivery receipt       | The PEC reached the recipient's mailbox                                                      |
| daticert.xml           | The machine-readable part of every receipt: type, dates, sender, recipient, errors           |
| Queue                  | A RabbitMQ letterbox: messages stay there until someone takes them                           |
| Publisher confirm      | RabbitMQ's answer to the publisher: "stored" (ack) or "no" (nack)                            |
| `ack` / `nack`         | The reader tells RabbitMQ "done, remove it" or "put it back"                                 |
| `mandatory`            | Asks RabbitMQ to return a message it cannot route to any queue, instead of dropping it       |
| Prefetch (`basic_qos`) | How many messages the reader receives ahead, before acknowledging them                       |
| `eventId`              | The stable identifier of an event: the same fact always has the same `eventId`               |
